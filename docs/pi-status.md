# pi status integration

Workbench adds one `--extension <bundled pi-extension.mjs>` to each pi invocation, before an argument delimiter if present. Existing explicit extensions, discovery settings, model arguments and saved Agent Settings remain unchanged. pi's `--no-extensions` disables discovery but still permits explicit extension paths. The observer registers only notification handlers through pi's official extension API; it does not register tools, change prompts, answer UI, cancel operations or replace user extensions. No permanent configuration or trust changes are made.

The bundled file is a shared application asset, not a launch-specific temporary configuration. Launch-local credentials and observations are revoked and removed by the existing Workbench lifecycle. Delivery state exists inside the pi process and ends with it; there is no extra process, polling or persistent observation data. Missing extension support or failure to load leaves the running terminal at Error without preventing input.

## Source and delivery

The extension captures the launch capability from `VIBEBRIDGE_STATUS_CONTEXT` and reports only to the loopback endpoint. It subscribes to its own extension runner, not a child agent's event stream. A separately launched child pi does not receive the observer's explicit extension argument merely by inheriting the environment. Do not explicitly install the Workbench observer into auxiliary sessions or user-wide extension configuration.

Each callback captures its facts before any asynchronous delivery. One ordered queue and sequence cover the main pi instance, including non-awaited UI notifications. `/reload` retains this sequence in the same process. Transport failures never throw into pi or return extension decisions; the next delivery reports observation loss before fresh evidence. A silent or permanently unreachable reporter cannot guarantee notification of its own failure. No inactivity timeout infers failure or recovery.

Reports contain event names, assistant role/stopReason, idle/pending flags and compaction outcome flags. Prompt text, UI titles, tool arguments/results, model messages and credentials are not forwarded as event content. Source validation, run credentials, ordering, child-scope rejection and projection follow [the shared contract](processing-status.md).

## Interpretation

- Session start/switch/fork/tree establish Ready when idle, or Busy if the official context reports ongoing work. `agent_start` clears the previous outcome and starts Busy.
- Ordinary tool activity stays Busy; individual tool failure does not end a turn. `agent_end` does not establish an outcome. Retry delays and automatic continuations retain Busy until a later reliable fact.
- `ui_prompt_start/end` delimit pi's coalesced outer blocking extension UI span. Waiting has priority over tool, compaction and agent activity. On release, active/pending work is Busy; otherwise the latest established idle/result fact becomes visible. This does not detect every natural-language question, tool approval or custom interaction.
- Assistant `message_end.stopReason` is cached only for the current run segment, then corrected from the last assistant in `agent_end.messages` after all user message replacement handlers have run. This samples no older session history and does not treat `agent_end` as completion. `agent_settled` with no active/pending work resolves `stop` to Done and other final failures to Error. `aborted` returns Ready only with explicit `isIdle: true` and `hasPendingMessages: false`. Missing outcome, length-limited output or an unfinished tool-call outcome is Error. New work clears prior outcome evidence.
- Official extension compaction callbacks are `session_before_compact`, `session_compact` and `session_compact_failed`. Processing and retries remain Busy. A failed automatic compaction is retained until final settlement unless a new agent segment or a newer assistant outcome establishes recovery, including continuation within the same tool loop. Completed manual compaction restores its prior idle/result fact; manual failure is Error. Cancelling compaction alone is not proof of main-turn interruption.
- Shutdown/unload reports observation unavailable. Reload or subsequent reliable events can establish a fresh state; cached success cannot survive observation loss.

## Evidence limits

The implementation follows the installed pi extension interface and [official extension documentation](https://github.com/earendil-works/pi/blob/v0.84.4/packages/coding-agent/docs/extensions.md). Automatic retry and low-level compaction notifications are not all extension events in that interface; their names in other APIs do not imply extension delivery. An interruption during retry backoff may have no new aborted assistant message, so it may remain Error when settled. Compaction that fails before its before-callback, or is intercepted by an earlier user extension, may provide incomplete observations. Existing extensions can initiate additional work during settlement; the observer samples official idle and pending facts but cannot predict work initiated by a later handler.

Version-specific real CLI traces, model/account conditions, known deviations and unverified scenarios belong to [#93](https://github.com/a1457139709/VibeBridge/issues/93), with support evidence tracked per CLI in [#85](https://github.com/a1457139709/VibeBridge/issues/85). Simulated extension/PTY checks and production UI tests are separate from real CLI support evidence. There is no historical compatibility matrix or enforced version floor.
