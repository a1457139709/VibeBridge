# Workbench 只做协调，状态归功能模块

主进程的 `Workbench` 是 IPC 进来的地方，但它不持有功能的状态。每个功能有自己的模块，模块持有自己的状态，并自己读写存储。`Workbench` 只做跨模块的事：

- **操作队列**：改动项目的调用一次一个地排队执行。
- **找项目**：把项目 ID 换成项目，项目不存在就报错。
- **跨模块流程**：创建、编辑、删除、激活项目要同时动存储和几个模块，流程写在 `Workbench` 里。
- **快照和事件**：把各模块的视图拼成快照，发给渲染进程。

一个调用既不进队列、也不找项目、也不组合模块时，IPC 直接调模块；`Workbench` 里不留只转发的方法，静态检查会拒绝它们。新功能加一个模块，`Workbench` 最多加一行排队，或在跨模块流程里加一步。

## Considered Options

- **状态都放在 `Workbench` 里**：每个功能都要改同一个文件，文件一直变大。
- **IPC 全部绕开 `Workbench`，直接调模块**：改动项目的调用会失去操作队列和找项目这一步，顺序和「项目已删除」的错误要在每个模块里重做一遍。
- **保留转发方法，让 IPC 只认识 `Workbench`**：每个功能的每个调用都要在 `Workbench` 里多一个方法，`Workbench` 又会变成所有功能都要改的地方。

## Consequences

- `Workbench` 只随跨模块流程变化；单个功能的改动落在它自己的模块和 IPC 那一行。
