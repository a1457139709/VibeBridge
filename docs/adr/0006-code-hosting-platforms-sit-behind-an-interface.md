# 代码托管平台藏在接口后面，GitHub 是第一个适配器

仓库绑定、issue 与合并请求视图、派发都要读写代码托管平台。工作台只通过一个平台无关的**代码托管平台接口**使用平台，每个平台一个适配器，放在一张封闭的表里（与 Agent 类型状态适配器的表同一种做法）。GitHub 是第一个、也是目前唯一的适配器，也是唯一调用 `gh` 的地方。以后接 GitLab 等平台时，只新增一个适配器。

- **仓库引用 = 平台 ID + 仓库路径**。路径是平台自己的仓库路径，不限定为两段的 `owner/repo`（GitLab 有嵌套 group），适配器之外不拆分它。仓库绑定和派发记录都存这两项。
- **领域形状**：接口只返回领域形状，命名平台无关（代码里叫合并请求，不叫 PR），不暴露 CLI 的输出格式。
- **四类失败**：未安装、未登录、无法访问、暂时性失败，都带上平台返回的原文。平台显示名、CLI 名、安装链接和登录命令由适配器提供。
- **能力声明**：子 issue、原生阻塞、合并方式、merge queue、必需检查这类平台差异由适配器声明，平台没有的能力 UI 不显示。具体能力随用到它们的功能加入。
- **默认平台**：未绑定的项目从默认平台列出可绑定的仓库。出现第二个适配器时，再决定用户怎样选择平台。

## Considered Options

- **直接做 GitHub 网关**：接口更简单，但仓库引用、失败类型、命名都会带上 GitHub 的形状，接第二个平台时要改存储格式，而编码规范不写迁移代码。
- **现在就实现第二个适配器**：能验证接口，但没有实际需求；只留接缝。

## Consequences

- `projects.sqlite` 里的仓库绑定存平台 ID 和路径；平台 ID 不在适配器表里时，按存储规则整体读取失败。
- 「GitHub 以外的平台」仍不在范围内，UI 文字暂时沿用 GitHub 的说法（如「Pull requests」）。
