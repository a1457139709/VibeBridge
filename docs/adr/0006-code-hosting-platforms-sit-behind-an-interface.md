# 代码托管平台藏在接口后面，GitHub 是第一个适配器

仓库绑定、issue 与合并请求视图和派发都只依赖一个平台无关的代码托管平台接口；GitHub 是第一个、目前唯一的适配器，以后接入 GitLab 等平台时只新增一个适配器。适配器放在一张封闭的表里，做法与 Agent 类型的状态适配器相同：

- **仓库引用 = 平台 ID + 仓库路径**。路径是平台自己的仓库路径，不限定为两段的 `owner/repo`（GitLab 有嵌套 group）。仓库绑定和派发记录都存这两项。
- **只返回领域形状**：接口的命名与平台无关（例如合并请求而不是 PR），不暴露平台 CLI 的输出格式。UI 文字可以沿用平台自己的叫法。
- **四类失败**：工具未安装、未登录、无法访问（仓库不存在与没有权限区分不开）、暂时性失败，都带上平台返回的原文。安装链接、登录命令和平台显示名由适配器提供。
- **能力声明**：子 issue、原生阻塞、合并方式、merge queue、必需检查等平台差异由适配器声明，平台没有的能力 UI 不显示。
- **唯一调用平台 CLI 的地方是它的适配器**。适配器用 Agent 运行实例所用的同一份登录 shell 环境，从其中的 `PATH` 找 CLI；工作台不读取也不保存凭据（见 ADR 0004）。

## Considered Options

- **只做 GitHub 网关**：实现最直接，但仓库绑定、派发记录会存下 `owner/repo` 这样的 GitHub 形状，界面也会认识 GitHub 的字段；以后接入第二个平台要改存储格式和所有调用方，而编码规范不写迁移代码。

## Consequences

- 存储里的仓库引用从一开始就带平台 ID；未知的平台 ID 按存储读取规则使整体读取失败。
- 新增平台时，除了适配器，还要按 ADR 0004 的原则确定它的身份来源，并在能力声明里写清它支持哪些功能。
