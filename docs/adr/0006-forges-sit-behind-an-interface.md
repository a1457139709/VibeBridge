# Forge 藏在接口后面，每个 Forge 一个适配器

仓库绑定、issue 与 pull request 视图、派发都要读写 Forge。工作台只通过一个与具体 Forge 无关的 **Forge 接口**使用它，每个 Forge 一个适配器，放在一张封闭的表里（与 Agent 类型状态适配器的表同一种做法）。接入新的 Forge 只新增一个适配器。

- **仓库引用 = Forge ID + 主机 + 仓库 ID + 仓库路径**。前三项确定是哪个仓库：
  - 主机是仓库所在的 Forge 实例，例如 `github.com`。自建实例的仓库 ID 只在本实例内唯一，所以引用要带主机。
  - 仓库 ID 是 Forge 自己给仓库的 ID，改名和转移都不变；GitHub 用数字 `databaseId`（REST 里的 `id`），不用正在换格式的 node ID。
  - 路径是最近一次见到仓库的位置，即该 Forge 自己的仓库路径。层级因 Forge 而异，适配器之外不拆分它。
  - 仓库绑定和派发记录都存这四项；判断两个引用是否同一个仓库只比较前三项。
- **按 ID 跟随仓库**：每次读写绑定的仓库前，适配器先找到它的当前路径。路径变了（改名或转移）就把绑定更新到新路径；仓库已删除、当前账号看不到它，或原路径上已是另一个仓库时，按「无法访问」处理。
  - GitHub 先用 GraphQL 按路径查，比对返回的 `databaseId`：一致就用返回的当前路径。路径查不到，或查到的是另一个仓库时，才用文档之外的 `repositories/{id}` 按 ID 查。主流程只依赖有文档的接口。
- **领域形状**：接口只返回领域形状，命名与具体 Forge 无关，不暴露 CLI 的输出格式。
- **四类失败**：未安装、未登录、无法访问、暂时性失败，都带上 Forge 返回的原文；怎样呈现和恢复由适配器提供。
- **能力声明**：Forge 之间的功能差异由适配器声明，Forge 没有的能力 UI 不显示。
- **默认 Forge**：未绑定的项目从默认 Forge 的默认主机列出可绑定的仓库；出现第二个适配器或第二个主机时，再决定用户怎样选择。

## Considered Options

- **直接对接单一 Forge**：接口更简单，但仓库引用、失败类型和命名都会带上那个 Forge 的形状，接第二个时要改存储格式，而编码规范不写迁移代码。
- **现在就实现第二个适配器**：能验证接口，但没有实际需求；只留接缝。
- **只存路径，靠 Forge 的重定向更正路径**：改名后 GitHub、GitLab、Gitea 一般会把旧路径重定向到新路径，可以据此更正。但重定向会失效（有人在旧路径新建同名仓库或 fork），Bitbucket 和 Azure DevOps 的文档也没有承诺重定向；仓库删除后又建了同名仓库时，只存路径会悄悄跟到新仓库上。五个主流 Forge 都有改名后不变、可按 ID 查到当前路径的仓库 ID，所以引用存 ID。
- **等接自建实例时再加主机**：那时要再改一次存储格式。主机现在就进入引用；GitHub 适配器通过 `GH_HOST` 把它交给 `gh`。

## Consequences

- `projects.sqlite` 里的仓库绑定和派发记录都存 Forge ID、主机、仓库 ID 和路径；Forge ID 不在适配器表里，或主机、仓库 ID、路径为空时，按存储规则整体读取失败。
- 不带仓库 ID 的绑定和派发记录认不出是哪个仓库：存储打开时删除这两张旧表，项目保留，变成未绑定，需要重新绑定，之前的派发记录不再显示。这是「不写迁移代码」之外的一次例外：只丢弃旧数据，不转换。
- 仓库改名或转移后，下一次读写或打开编辑项目对话框时，绑定会跟到新路径；派发记录按仓库 ID 匹配，换路径后仍然显示。
