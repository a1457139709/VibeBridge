# 测试是行为的保障，判定只取决于行为是否成立

测试是代码行为的保障。每个测试规定一项行为，并且对同一份代码，在任何机器、任何负载下都给出同一个判定。判定只取决于这项行为是否成立，与执行快慢无关。

由此确定测试的写法：

- **分层**：能用单元测试证明的行为，就写成单元测试；组件测试负责 UI 交互。desktop 套件只覆盖必须有真实 Electron、操作系统或 PTY 才能测的行为：原生输入、真实窗口几何和拖拽、进程生命周期、重启后的恢复，以及 preload/IPC 的连线。
- **断言精确的程序输出**：desktop 套件优先断言 `window.workbench.snapshot()` 返回的结构化状态，以及 CLI fixture 的输出；只有行为本身就是"屏幕上显示什么"时，才断言屏幕文字、渲染结果或 CSS。
- **只等会发生的事，并且等它的最终状态**：desktop 套件用 `until(最终状态)` 等待，条件写成行为最终停在的值，所以状态先到后到都能通过。需要知道程序状态时主动查询，例如给 `tests/fixtures/interactive.cjs` 发 `size` 再等它的回复，而不是清空输出、等一个可能已经发生过的被动事件。
- **"不会发生"在单元测试里同步证明**：在真实环境里等多久都证明不了某事不会发生，所以这类断言放进单元测试，由测试控制输入和时间，同步断言结果。
- **测试里没有固定时长或固定帧数的等待**：不写"等 N 毫秒或 N 帧之后再断言"。
- **不为测试增加产品功能**：产品代码里不加只供测试使用的接口，比如表示"已稳定"的 `workbench.idle()`。测试用已有的 `snapshot()`、fixture 查询和单元测试来达到确定性。
