# 代码里不写注释，决策记在 ADR 里

源代码不写注释。代码做什么由名字和结构表达；为什么这样做，凡是从代码里看不出来、又会约束以后改动的决策，写进 `docs/adr/`。一条注释只会是下面四种之一：

- **复述**：重复代码里已经看得到的东西。删掉。
- **过时**：说的是已经不存在的代码或实现。删掉。
- **借口**：为一个凑合的实现开脱，让它被照抄下去。删掉，并开一个 issue 去修那个实现。
- **决策记录**：记下一个重要、看代码看不出来的决定。写成 ADR，再删掉。

ADR 只记决策：决定了什么、为什么、放弃了哪些方案，用领域语言写，不写文件路径、函数名和外部工具的行为细节。代码能表达的事实留在代码和测试里；外部程序的行为由测试替身和测试固定下来，而不是写成文档。

工具指令不是写给人看的注释，可以保留。现有的注释由一个只降不升的基线检查，逐步清理。

## Considered Options

- **用 oxlint 的规则**：oxlint 没有禁止注释的规则，也不支持按文件计数的基线；仓库已有的检查脚本用 TypeScript 语法树写，这里沿用同一种做法。
- **只禁止新增的 `//` 注释，保留 JSDoc**：JSDoc 正是这个仓库里绝大多数复述的来源，保留它等于保留问题。
- **一次删完，不要基线**：决策记录要逐条读、逐条写成 ADR，一次改动未必做得完；基线让剩下的注释不再增加，又不挡住这次合并。
- **把注释搬进文档**：只是换个地方存放复述和实现细节，文档随代码一起过时，没人维护。

## Consequences

- 读代码的人要找「为什么」时去看 ADR。
- 单看调用处说不清它做什么的名字，就该改名，而不是补注释。
